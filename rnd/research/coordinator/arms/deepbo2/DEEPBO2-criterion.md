# DEEPBO2: can a cheap selector capture the best-of-2 gain of the deep tier? (frozen 2026-10-10 10:5x, coordinator; r4to's standing instruction 2026-10-08: run autonomously)

Question: over the two existing seeds of the recommended deep configuration (DT512 arm H: cut 6 + Qwen3.6-35B + thinking 512, V-para 51 judged ids, Opus judge.v1 rows s42 and s43), the oracle best-of-2 scores ≈ +0.04 raw over a single seed (handoff 10-10 §4.3: 0.553 → 0.590, CI +0.027…+0.051). A device could generate two answers at ≈ the 1024-budget time. Does a selector that never sees the judge capture a useful part of that gain? Measured with 0 new generations and 0 new judge calls on the answers.

## Fixed inputs
- Candidates per item: H's s42 and s43 answers (`blind/V-para/runs-dt512/dh-H-vpara-s{42,43}.traces.jsonl`), scored by their existing Opus rows (`…judgments.jsonl`, both orders, judge-core combineOrders; disagreement = tie) on `runs-cut6/judged.ids` (51).
- Selectors (each reads question + answer A + answer B only, no sources, no judge output; both presentation orders; a pick counts only if both orders agree, otherwise fall back to seed 42; temperature 0, ≤ 8 output tokens, thinking off):
  - **S1 SELF**: Qwen3.6-35B-A3B UD-Q2_K_XL (sha 96b9c0af…) via llama-server b11010 CPU on the mini (same flags as the dt512 runner's server: `-t 4 -tb 4 -c 4096 -ngl 0 --jinja --reasoning-format deepseek`, `chat_template_kwargs.enable_thinking=false`).
  - **S2 VERIFIER-4B**: Qwen3-4B-Instruct-2507 Q4_K_M (sha 36058033…), same server flags (the engine's "verifier" role, as a 4B on the device would do it).
  - Prompt (frozen in `tools/select.py`, sha recorded in DEEPBO2.md): one English system line ("You compare two answers to the same question and reply with exactly one letter: A or B, the more accurate, complete and well-sourced answer."), user = question, "Answer A:", A, "Answer B:", B, "Which is better? Reply A or B."; parse the first A/B letter in the reply; anything else = no pick.
- Free baselines on the same rows: oracle (max per item, judge-informed: an upper bound that includes judge noise), anti-oracle, always-s42, always-s43, expected random = mean of the two singles, heuristic "longer answer (tokens)", heuristic "more citations". 
- Scales: ratio and floor-adjusted exactly as paired.mjs (judge-core summarize; floor Σ(boar−1)/Σ(ref−1)); paired Δ (items resampled jointly, 2000 boots, seed 7) of each selector's picked set vs (i) the single-seed mean (reported as Δ vs s42 and vs s43 separately plus their average), (ii) the oracle; per-selector agreement with the oracle (% items where the pick equals the oracle's strict winner, ties excluded), position consistency (% items where both orders agreed).
- Script-only scoped exception: `tools/` scripts read the questions and answers; the coordinator's and any agent's context hold ids, counts, hashes, aggregates only; selector models read 51 items × 2 answers × 2 orders each (logged in EXPOSURES as a model read, not a generation).
## Rules (strict)
- A selector is **USEFUL** if its paired Δ vs **both** single seeds has CI low > 0 and the average point Δ ≥ +0.015 (≈ 40 % of the oracle's +0.038); **WEAK** if CI low > 0 vs both but point < +0.015; else **NO**. A heuristic baseline that is USEFUL is reported as such (it would be free on a device).
- No prompt iteration after seeing results: one prompt, one run per selector. A parse failure rate > 10 % on a selector = FAIL-INFRA for that selector (report, do not retry with another prompt).
- Mini: never while another heavy job runs (heavy lock); one llama-server at a time; S2 first (≈ 10 min), S1 after (≈ 1–1.5 h, prefill-bound: 204 prompts of ≈ 500–900 tokens); disk ≥ 25 GiB, swap ≤ 8 GB, detector untouched. Judge calls: 0. Wall cap 2.5 h.
