# SFT4B stage 1 — can it fit in the mini's 33 GiB without deletions? (2026-10-13 21:0x; opus/high research agent, a parallel session; coordinator saved the text verbatim, entities unescaped)

**Answer: yes, via path (b):** train the LoRA in MLX on an 8-bit MLX copy of the base, export ONLY the adapter, convert it with llama.cpp's `convert_lora_to_gguf.py` (config-only `--base`), and let llama-server load it on top of the existing claim Q4_K_M with `--lora`. Peak extra disk ≈ 4.6 GiB → ≈ 28.4 GiB free (3.4 GiB above the 25 GiB floor). The frozen criterion (sha 5853b8ea…) names bf16, merged weights and a requantised model, so stage 1 needs a frozen addendum first (see SFT4B-criterion-addendum-1.md). The mini showed 34 GiB free at check time. Labels (a)–(d) below are path labels, not disk-policy classes.

## 2. Recommendation: path (b) with the 8-bit base

Addendum content (frozen separately): training base = mlx-community 8-bit instead of bf16; X = the claim Q4_K_M + the runtime GGUF LoRA (f16), adapter model id `qwen3-4b-instruct-2507-q4km-sft4b`; chat template pinned to Qwen's original; `grad_checkpoint: true` (memory only); rank 16, scale 20 (= alpha 320), lr 1e-5, 2 epochs (600 iterations at batch 4), seed 42, prompt masking unchanged.

Pins: mlx 0.32.3, mlx-lm 0.32.0, llama.cpp b11010 (4bc272f), huggingface_hub 2.2.0, gguf-py 0.19.0 from that tree; all already in `<runner>/kiln/sft4b/.venv`. The mini's login shell is fish → steps as bash scripts under `tools/mini/`. Variables: `K=<runner>/kiln/sft4b; V=$K/.venv/bin; L=<runner>/spikes/llama-b11010; M=<runner>/shared-models/hf/Qwen3-4B-Instruct-2507-mlx8`.

1. **Disk gate:** refuse unless free − 5 GiB ≥ 28 GiB.
2. **Base download:** `$V/hf download mlx-community/Qwen3-4B-Instruct-2507-8bit --revision 0e42af58449718de7931ee04f28191fbe6c43a56 --local-dir $M`. Check `shasum -a 256 $M/model.safetensors` = `a6d98b6b22bd3928f0a9e38aea84c085e678bba1e03d028f21cbf6e0f6ed9f2c` (4,274,158,989 B). Check `df` dropped ≈ 4.0 GiB (nothing duplicated into `~/.cache`).
3. **Config-only directory:** `$V/hf download Qwen/Qwen3-4B-Instruct-2507 config.json generation_config.json tokenizer_config.json tokenizer.json vocab.json merges.txt --revision cdbee75f17c01a7cc42f958dc650907174af0554 --local-dir $K/base-config` (~16 MB).
4. **Pin the template (required).** The mlx-community `chat_template.jinja` (sha 40c21f34…) adds `<think>\n\n</think>\n\n` to a final assistant turn: training with it teaches an empty think block that inference never prompts. Overwrite `$M/chat_template.jinja` with the `chat_template` from `$K/base-config/tokenizer_config.json` (sha 64f85b19…). Render `train.jsonl[0]` with mlx-lm's tokenizer and assert: no `<think>`, and the target is exactly `<|im_start|>assistant\n` + answer + `<|im_end|>`. The claim GGUF's generation prompt is also plain `<|im_start|>assistant\n`.
5. **Smoke:** `tools/mini/smoke_lora.sh` with `model: $M` and `grad_checkpoint: true`. Log tokens/s, peak memory, max RSS, `df`. Stop if rc ≠ 0 or peak memory > 11 GB; fallback = the 4-bit repo `mlx-community/Qwen3-4B-Instruct-2507-4bit` @ `50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b` (2,263,022,417 B; peak 2.8 GiB), same template fix.
6. **Train:** smoke config + data `$K/train/data/{train.jsonl = data/train.jsonl, valid.jsonl = data/holdout.jsonl}`; `iters: 600`, `save_every: 200`, `steps_per_eval: 100`, `val_batches: -1`, `grad_checkpoint: true`; `nohup $V/python -m mlx_lm lora -c $K/train/config.yaml > $K/train/log 2>&1 &`; watchdog kills the job if free < 27 GiB (macOS swap files grow on the same disk); resume with `resume_adapter_file: $K/train/adapter/0000400_adapters.safetensors` and fewer iterations. Hold-out loss in the log: iteration-1 validation loss = base model (LoRA starts at zero), last = trained adapter.
7. **MLX → PEFT** (`tools/mlx2peft.py`, ~25 lines): key `model.layers.N.<proj>.lora_a` (in × r) → `base_model.model.…lora_A.weight` = transpose (r × in); `lora_b` (r × out) → `lora_B.weight` = transpose (out × r); `adapter_config.json` = `{"peft_type":"LORA","r":16,"lora_alpha":320,"target_modules":[q,k,v,o,gate,up,down],"base_model_name_or_path":"Qwen/Qwen3-4B-Instruct-2507"}`. llama.cpp applies scale = alpha/rank = 20 = MLX's scale.
8. **Convert:** `$V/python $L/convert_lora_to_gguf.py --base $K/base-config --outtype f16 --outfile $K/export/qwen3-4b-instruct-2507-sft4b-lora-f16.gguf $K/peft` (≈ 63 MiB, 252 tensor pairs).
9. **Clean up** after P1: delete `$K/train/adapter/0000{200,400}_adapters.safetensors` and `$K/peft` (pipeline-created). Keep the final adapter and the GGUF; keep `$M` until the verdict (P2 and hold-out generations need it), then delete it.
10. **Parity P0–P2** (§3) on the mini with `$L/build-cpu/bin/llama-server` and `<runner>/shared-models/Qwen3-4B-Instruct-2507-Q4_K_M.gguf`. One heavy job at a time; :8094 stays up.
11. **MacBook:** copy the GGUF LoRA to `shared-models/`, DISK-LOG + MODELS rows; side-tree adapter patch: `adapter.ts:429-431` builds server args with no `--lora` → add `--lora ${BOAR_SERVER_LORA}` when set and record the LoRA sha in `versions`; same in `runner/parallel.sh:20` if used; the side tree needs its own adapter sha (`run_selftest.sh:13` checks 6298e5d3); then stage 2 as frozen.

## 3. Parity checks
- **P0 identity:** claim GGUF with `--lora-scaled <lora>:0` vs no LoRA, greedy (temp 0, seed 42), 10 rendered self-test prompts → byte-identical 10/10 (loading the adapter changes nothing by itself).
- **P1 conversion math:** for 6 tensors (q, k, down in layers 0, 17, 35) compare the weight change from MLX (`20 · lora_bᵀ · lora_aᵀ`) with the GGUF's (`alpha/r · B·A`, read with gguf-py): max relative difference ≤ 2e-3 (f16 rounding). Catches transpose, naming and alpha errors.
- **P2 behaviour:** 10 hold-out + the 10 P0 prompts, greedy, ≤ 200 tokens, four arms: M0 = MLX 8-bit base, M1 = MLX 8-bit + adapter (`mlx_lm.load(…, adapter_path=…)`), G0 = claim Q4_K_M, G1 = G0 + GGUF LoRA. First check llama-server `/apply-template` = HF `apply_chat_template` per prompt. Pass if: G1 ≠ G0 on ≥ 8/20; the adapter's effect has the same sign in both engines (median answer length, citation-marker pattern); M1/G1 agreement (exact match + first-divergence token) ≥ M0/G0 agreement − 2 items. If exact agreement is low: Haiku pairwise M1 vs G1 equivalent on ≥ 16/20. Log tokens/s G0 vs G1 (runtime LoRA cost).
