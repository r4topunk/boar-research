## Premise correction (read from SEFIX-F1.patch before the run)
F1 does not read chunk vectors and they are not float: rsSeLead scans the full **int8 lead-vector matrix** (one 384-B vector per thread, lead_vecs) of each Stack Exchange pack without chunk_vecs. In the SEFIX-124 kit that is qa-cooking-se (25,698 threads, 9.87 MB) + qa-money-se (35,102, 13.48 MB) = **23.35 MB scanned per question** (cached in RAM after the first query; health/travel/outdoors v3proto have chunk_vecs, F1 skips them). So the "int8 estimate" is the current state; float32 would be 93.4 MB/q.
W78 path: Hamming of sign(query) over the bit-packed sign sidecar (48 B/thread) -> top-N -> exact int8 cosine of only those N rows (SELECT ... WHERE article_id IN, same arithmetic incl. the float32 norm) -> unchanged F1 rule (tau 0.78, 1 thread).

## Verdict (frozen rule)
W32: (a) 42 of 42 delivered (>= 41) PASS; (b) 0 of 11 health items changed PASS; (c) 0.126x bytes (<= 0.25) PASS -> **ADOPT-CANDIDATE, N = 32** (smallest N in the criterion set). W64/W128 also pass. Post hoc: the first loss appears at N = 8 (cooking-009, 4 picks differ), N = 16 already drifts in 2 reason codes, so N = 32 has a 2x margin on this set. Lossless here because F1 only acts at cosine >= 0.78, where sign-Hamming ranks the true top thread inside the top 16.
Sidecar is additive (+3.16 MB, 1.4 % of the two packs' 226 MB): lead_vecs stays for the rescore and the other lead paths.
