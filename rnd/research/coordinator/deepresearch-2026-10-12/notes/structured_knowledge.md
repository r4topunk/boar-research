# Structured knowledge, places and tools on device (deep research 2026-10-12, angle `structured_knowledge`)

State as of 2026-10-12. Read-only sweep: about 40 tool calls (WebSearch/WebFetch, the GitHub API via `gh`, the HF Hub API, the OSM taginfo API, and HEAD requests for dump sizes). Nothing over 100 MB was downloaded, and blind/ and veil/ were not touched. Internal baselines come from arms/facts/*, arms/cf/*, KNOWLEDGE-PACK-SIZING.md, CLOSED.md and QUEUE.md (VENUEGPS-2).

## TL;DR
- **Raising FACTS recall will not move the bench.** FACTS fires on 0/110 v0.2 and 0/58 V-para items, because the bench questions are not single-slot lookups. The structured-knowledge lever that can still matter is a **facts block injected as context** for comparison and multi-hop items. At 3–8B, KG-Infused RAG reports +4 to +11 pts on 2WikiMultihopQA, a comparison-heavy set, and +5 to +7 on MuSiQue over vanilla RAG, using Wikidata5M (CC0) — https://arxiv.org/html/2506.09542v2. It needs several LLM calls per query, so on the phone the triple selection must be made deterministic.
- **Full GraphRAG does not suit a 4B.** With SLMs (1.5–4B), MS-GraphRAG fails to produce answers and LightRAG falls below naive RAG (MultiHop-RAG: Qwen2.5-3B 21.9 vs naive 39.5). MiniRAG (a chunk+entity heterogeneous graph) gets 48.6 vs 39.5 with the same 3B, at 25 % of LightRAG's storage — https://arxiv.org/html/2501.06713v3. GraphRAG-Bench (ICLR 2026) finds that vanilla RAG matches or beats GraphRAG on fact retrieval, and that graphs help reasoning and summarisation at up to 100k+ prompt tokens per query — https://arxiv.org/html/2506.05690v3.
- **We have no 0-call answer to whether Wikidata holds our missing facts.** LOSSMAP/WIKISECTION found the facts outside Wikipedia on 12/13 items. Wikidata is largely Wikipedia-derived, so the prior is low. The next step is a WIKISECTION-style jev gate against Wikidata entity statements, not a build (proposal WDGATE below).
- **Places: hours and closures are the open problems, not coverage.** No `opening_hours` field exists in Overture places or in Foursquare OS Places, and Overture `operating_status` has been null by default since 2026-05 (only US signals are refreshed). OSM has `opening_hours` on 23.5 % of 1.62M restaurants and on 75.6 % of the 68k `diet:vegan` objects (taginfo, data 2026-10-12) — https://taginfo.openstreetmap.org/keys/diet:vegan. a competitor team's 25.3M-place DB (3.5 GB, about 140 B/place) reports closed places as "the main error left" (44 in one grading) and mislabelled Overture categories — [competitor link removed]
- **Two more closure and hours sources fit the licence rules.** Foursquare OS Places (Apache-2.0, monthly, latest dt=2026-09-15, gated on HF) carries `date_closed` plus `unresolved_flags` (closed/doesnt_exist) — https://docs.foursquare.com/data-products/docs/places-os-data-schema. AllThePlaces (data CC0, weekly, 20M+ POIs from 4,100+ brand-site spiders) is the source of chain stores — https://www.alltheplaces.xyz/.
- **Cheap deterministic travel tools all have small open data:** time zone per city (the GeoNames column we already ship plus Android ICU, so 0 new bytes), sun times (suncalc, BSD-2), currency (ECB full history 641 KB; fawazahmed0 exchange-api CC0, 200+ currencies), visas (passport-index CSV, MIT, 199×199; successor repo updated 2026-03) — https://github.com/ilyankou/passport-index-dataset. Plug types should not come from Wikidata: our CF review found 7/30 disagree and 5/30 unclear.
- **No open drug-interaction table permits redistribution.** The NLM RxNav DDI API was retired around 2024-01-02, DDInter is CC BY-NC-SA, and DrugBank is non-commercial. The open routes are MedlinePlus XML (attribution; ASHP drug monographs are excluded) and openFDA label text (public domain) — https://blog.drugbank.com/nih-discontinues-their-drug-interaction-api/.
- **Text-to-SQL/SPARQL on the phone is out of reach.** SLM-SQL-1.5B reaches 67.1 % BIRD dev EX only with 64 sampled candidates plus a merge model (61.95 % with self-consistency alone) — https://arxiv.org/html/2507.22478v1. A full Wikidata SPARQL engine is a server job: truthy dump 43.5 GB bz2 (2026-10-09); QLever docs cite 128 GB RAM / 3 TB SSD for older Wikidata builds. The phone-sized pattern is a fixed schema plus grammar-constrained slot frames (llama.cpp GBNF) and deterministic SQL.

## Proposed actions (ranked)
1. **WDGATE (0 Claude calls, jev only, [usage detail removed], ≈ 1 h):** take the absent-knowledge and wrong-fact items from LOSSMAP/WIKISECTION (rationale terms only, script-only, as in H5b). For each, resolve the on-topic entities to QIDs (QLever or WDQS public endpoint) and ask jev whether any statement of those entities, or of their 1-hop neighbours, contains the missing fact. **Bar:** ≥ 30 % of items (≥ 40 % on comparison items) → an arm "facts block as context" (Wikidata5M-style entity cards in one kept slot for the deep tier). Below that → close "Wikidata as a knowledge source for the bench" (prior: low, because Wikidata is Wikipedia-derived and WIKISECTION found the facts outside Wikipedia).
2. **FSQ closure cross-check (0 judge calls; needs r4to to accept the HF gate):** match our area-tile venues to FSQ OS Places by name + 100 m and count `date_closed`/closed flags. If ≥ 3 % are flagged, add the drop rule; cost ≈ 0.5 agent-day. It attacks the closed-venue error that a competitor team names as its main residual.
3. **Travel slot tools (tz from GeoNames, suncalc, currency CC0 dated table, visa matrix):** each is < 1 MB and deterministic. Gate = count of dev items per slot type (v0.2/V-para aggregates via jev on question text categories, script-only); build only the slots with ≥ 2 items. Expected Δ is small (the CF precedent forecast +0.005 to +0.012).
