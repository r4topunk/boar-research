# TILE-PATH: the area-tile path end to end, and what a ruler current-city stratum needs (2026-10-21)

TL;DR (0 judge, 0 generation, 0 paid; no blind/, no rnd/veil, no bench/v0.4 file opened):
- **The tile path is a deterministic, LLM-free lookup over OSM food/drink records.** A device fix goes to `searchPois`, which reads the 1° tile(s) around it and returns up to 10 places ranked by OSM diet tag strength, then distance. Each line can carry the name, distance, address, diet tag and the raw OSM `opening_hours`. It runs in 5–192 ms (VENUEGPS-2).
- **Data is ready, the device apps are not.** All 8,374 world tiles are built (MacBook, 980 MB) and hosted (HF r4topunk/boar-packs @44c3375c, ODbL). The gazetteer (sha 215ce466…) carries the tile index. Neither phone app can run a current-city query with a location today:
  - BOAR Bench hard-codes "location unavailable".
  - The RN app wires GPS but has no Android permission UI and no user tile-download UI.
  - **The app maintainer's native Kotlin app (the submission) has no places code and no location permission.**
- **Only food/drink questions use tiles.** `detectGeoIntent` sends 6/13 v0.1 travel/place dev items to places (food-001/002/006, vx-003/4/5). The other 7 (trv-*, vit-trv-*, lan-exp-004/5/6) never touch a tile, and the device location is not passed to the model on any other route. TILE-PATH's kill criterion (1), as written over trv-*/lan-exp-*, would fail by construction (§6).
- **Tag sparsity is the main content risk.** Of 573 gazetteer cities with population ≥ 1M:
  - 144 (25 %) have ≥ 3 vegan-tagged OSM places within 3 km of the centroid.
  - 247 (43 %) have that many within 25 km, the engine's widest radius.
  - 13 have no tile at all.
  - Tile cost at the ruler's 25 km rule: median 0.28 MB per city, p90 2.1 MB, max 12.5 MB (Seoul).
- **Minimal stratum: 10 cities × 2 queries = 20 items.** Cities are drawn by a seeded rule with no venue inspection; tiles total about 5–30 MB. Venues are verified by people for exists, vegan and in-city, separately from the OSM gold, which is circular. A rival runs the same kit from the same pinned files and gets the location from Android's mock-location provider (§4).

## 2. How the engine picks and reads a tile at run time (wt/cut7 = claim build)

1. **Intent.** `detectGeoIntent(query)` returns null unless the question asks for places to eat or drink (geo.ts:165-197). "city I am / i'm in / near me / my location" sets `near: device` (geo.ts:125-126); a capitalised "in Lisbon" sets `near: place`. Diets: vegan, vegetarian, gluten_free, halal, kosher. Cuisine terms become the FTS text. Health questions skip this path (answer.ts:740-745).
2. **Pack gate.** `hasPlaces` = at least 1 file in `<documents>/poi/` (geoWiring.ts:28). Zero files gives "The offline places pack is not installed…" (answer.ts:462-466; geo.ts:449).
3. **Location.**
   - `near: device`: `getLocationFix` (≤ 5 min fix, else wait up to 10 s) or `getLocation` with a 700 ms timeout (answer.ts:254-256, 506-541).
   - Error (denied, unavailable, timeout): "I couldn't get your location… Which city are you in?" (geo.ts:430).
   - Stale fix: "The last one was in X… are you still there?" (geo.ts:437).
   - `near: place`: the gazetteer resolves the name to the **most populous** match (poiPack.ts:300-318); the packs' own city list is the fallback (geoWiring.ts:43-48).
4. **Tile choice.** No tile is chosen explicitly. Every `poi/*.sqlite` whose file name parses as a tile becomes an area with bbox = its 1° cell, opened lazily (pois.ts:92-111). `searchPoiPacks` queries every area whose bbox overlaps the search circle (poiPack.ts:224-246). `tileIdOf(lat, lon)` = floor of both coordinates, e.g. "t-N52E013" (poiRegions.ts:881-885). `tileIdsFor(lat, lon, km)` gives the 1–4 tiles a city circle touches (poiRegions.ts:897-907).
5. **Radius and filter.**
   - Radius starts at 3 km and widens to 10 km, then 25 km, until ≥ 3 exact, non-doubtful places match (poiPack.ts:16-17, 241-246).
   - Search: cell-range SQL, then category, then FTS text, then a haversine cut (poiPack.ts:142-171).
   - Diet: an OSM tag other than "no", or for Wikivoyage listings only, the diet word in the listing's own text (poiPack.ts:163-167). Nothing is inferred.
   - Coverage: "none" if no area contains the center, "full" or "partial" from 8 probe points (poiPack.ts:209-214).
6. **Ranking.**
   - Exact OSM places first, by diet strength (only 3 > yes 2 > limited 1), then distance.
   - Approximate Wikivoyage listings come next. Records whose build-time `diet_check` < 0.35 come last, flagged "to verify". Maximum 10 (poiPack.ts:247-260).
   - With a named city (no distance), places with an address come first (answer.ts:578-587).
   - `nearestPlaceIn` names the city for the fix: the most populous place ≥ 100k within 25 km (poiPack.ts:287-298).
7. **Rendered answer** (`formatPlacesAnswer`, geo.ts:315-386):
   - Header, e.g. "Vegan places near you in Berlin, Germany, ranked by the OpenStreetMap diet tag (only > options > limited), then distance:".
   - Numbered lines: **name — distance — address — "vegan: only/options/limited" — raw OSM opening_hours [n]**.
   - Then a "From the Wikivoyage guide (approximate location)" block, the line "'Best' here means the ranking above; ratings and popularity are not available offline", the search radius, and the OSM attribution with the extract date and a "tags and hours can be wrong" warning.
   - No phone or website appears in the text; they go in the source chunks (geo.ts:266-286).
   - Reason codes include `places:N`, `places:coverage-full|partial`, `places:region-t-…` and `places:near-city` (answer.ts:609).
8. **Empty cases.**
   - Tile present but no match: "The offline map near you has no place tagged vegan within 25 km, so I won't list any rather than guess" (geo.ts:400-427).
   - No tile covers the point: "I don't have offline place data near you, so I won't list any restaurants rather than guess" (geo.ts:389-394).
   - **The model is never called on this path** (answer.ts:734-735 comment). The device location is used only here: no other route reads `getLocation` (grep over wt/cut7/src).

## 4. Minimal plan for a ruler current-city stratum

| element | proposal | why |
|---|---|---|
| N cities | **10**, drawn by a seeded rule from the gazetteer: population ≥ 1M, 2 per continent (EU, AS, AF, AM-N, AM-S/OC), seed frozen, no venue or tag inspection (the same method as scripts/draw-poi-cities.mjs seed 20261003) | Fidelity to V2 "any city I am in"; the draw keeps sparse cities in on purpose |
| M queries | **2 per city**: V2 verbatim ("Tell me the best vegan restaurants in the city I am currently in") + one diet/cuisine variant written by a non-Claude model (e.g. vegetarian or a cuisine "near me") | V2 is the post author's only stated eval; the variant checks the path generalises past one string |
| Location | Gazetteer centroid of the drawn city (lat/lon to 4 decimals), frozen with the ids; the same fix for every arm and the reference | Deterministic; RULER-SPEC §2 already passes context to all arms |
| Tiles | `tileIdsFor(lat, lon, 25)` per RULER-SPEC §5.2 (note: the RN eval flow uses 15 km, answerEval.ts:38). From the sweep: 1–4 tiles per city, median 0.28 MB, p90 2.1 MB, so about 5–30 MB for 10 cities. Fetched by catalog sha, hashed before any arm answers. | §5.2 |
| Scoring | A person (or an open-web agent with a 20 % human spot check, BENCH-RULER O4) checks the top 5 names of each answer, for each arm and for the reference, on 3 booleans: **exists** (open listing or map hit dated 2025–26), **vegan** (vegan-only, or a menu with vegan dishes), **in city** (address inside the city or its metro). Item score = verified count ≥ 3 → task success, plus precision = verified / listed. OSM gold match is reported as a separate plumbing number. | OSM gold is circular: engine and gold come from the same tags (VENUEGPS-2 caveat 3) |
| Cost | About 2 h of human checking for 20 items × 2 arms (BENCH-RULER O4: about 1 h per 10 items); 0 LLM on the BOAR side (the places path is instant) | |
| Rival kit | Publish the city list, fixes, the tile shas (catalog rows) and gazetteer sha 215ce466…; files at HF r4topunk/boar-packs @44c3375c (ODbL / CC BY). A rival app gets the same fix from Android's developer-options "mock location app" (or `adb emu geo fix` on an emulator) and may install the same tiles or its own data. Score with the same 3-boolean sheet. | Same kit, same input, app-agnostic scoring |

Expected outcome before running (prior, not a result): sparse cities (Lagos 0 vegan-tagged within 25 km, Cairo 3, Mumbai 21 within 25 km but 3 within 3 km) get a refusal or a short list, while the web reference lists real places. The stratum will show the tag-sparsity gap. It is not a guaranteed win.

Dev check that can run now (MacBook, 0 LLM): the 6 dev items that do route to places (food-001/002/006, vx-003/4/5) already pass 6/6 (VEXACT-ACCEPT). The hypothesis's "≥ 3 POIs on ≥ 80 % of dev near-me items" should be re-scoped to **food/drink-intent items with a location**. ## 5. Risks

| risk | evidence | mitigation |
|---|---|---|
| Tag sparsity | 573 cities ≥ 1M: 25 % have ≥ 3 vegan-tagged places within 3 km, 43 % within 25 km. Tokyo's 9.9 MB tile has 188 vegan-tagged out of 62,475 POIs, and t-N35E140 has 2. | Report per-city tag counts with the stratum; the engine's refusal stays honest |
| Stale OSM | Snapshot 2026-09-25/27; there is no update path except a new gazetteer index (pois.ts:218-226) and re-download. Hours are raw OSM strings. | The answer already carries the extract date and the "tags and hours can be wrong" warning; human check catches closures |
| Cities without tiles | 13 of 573 ≥ 1M cities have no tile in the index | Draw rule excludes no-tile cities only if stated before the draw; otherwise they score as refusals |
| Name ambiguity (named-city path) | "Valencia" resolves to Valencia, Venezuela (0 vegan) and not Spain: most-populous wins (poiPack.ts:304-308) | The current-city stratum uses fixes, not names; flag for food-00x-style items |
| Tile radius mismatch | RN eval flow 15 km vs RULER-SPEC 25 km; kit-vexact lacks t-N38W009, which Lisbon's 25 km circle touches (still 6/6) | Freeze 25 km and the tile list by rule |
| Submission has no places path | Native Kotlin: 0 places code, no location permission | Decide before R4 (10-24): port, or mark the stratum unsupported for the native APK |
| "Best" is tag strength | Ranking = diet tag, then distance; no ratings offline (stated in the answer) | Human "vegan + exists" check, not "best" |

UNKNOWN:
- Whether the app maintainer plans a places/location feature in the native app before 10-31.
- Whether the RN Android catalog screen lists the 8,374 tile entries for manual download (asset provider registered; UI not checked).
- Single-city tile rebuild time.
- How a mock-location provider interacts with the RN module's LocationManager freshness check on a real phone (not tested).
- The tile ids of the 7 v0.4 location items (coordinator-only step; not run here).
- Whether a 25 km circle should count partial-coverage tiles at a country border.

## 6. Note on the TILE-PATH hypothesis wording
Method (1) names v0.1 trv-*, vit-trv-* and lan-exp-004/005/006 as the dev near-me set. `detectGeoIntent` returns null for all 7 of them: plugs, airport transfer, a walking estimate, Kyoto, the Sahara, Kilimanjaro (checked by running geo.ts on the public question strings). With a location and a tile they would still never reach places, so kill branch (1) would fire for reasons unrelated to tiles. The location-bearing items that matter are food/drink queries. The 7 v0.4 location items need the same intent check, by the coordinator, before they are counted as tile-path items in INPACK-STRATUM.
